# WR019: a container's port isn't published where the host connects

- **Layer:** 2, addressing
- **Confidence:** high when exactly one container explains it; medium when several containers could (they listen on the port unpublished, or publish it under another port or address), or when the host's own lookup of a container name couldn't run
- **Supersedes:** WR001
- **Since:** v0.1 (M2)

## The pitfall

From the host, a container's port is reachable through `localhost` only if it is **published** (`ports:` in Compose, `-p`). `EXPOSE` alone publishes nothing. Three variants:

1. **Not published:** the container listens on 8080, but nothing on the host does.
2. **Published under another host port:** `ports: ["18080:8080"]`, and the host uses `localhost:8080`.
3. **Published on another host address:** `ports: ["127.0.0.1:18090:8080"]`, and the host uses its LAN address (or the reverse).

And the host can't use container names at all: Docker's DNS answers them only inside Docker networks.

```
curl: (7) Failed to connect to localhost port 8080: Connection refused
```

## The evidence

| Evidence | What it shows |
|---|---|
| `docker.container` of the containers that publish or expose the port | their port bindings (`HostConfig.PortBindings`): host address and host port per container port |
| `netns.listeners` of the host | nothing on the host accepts the port at that address |
| `netns.listeners` of running containers | which container listens on the port without publishing it; whyreach reads at most 32 |
| `probe.dns` from the host | for a container name: the host's resolver doesn't know it |
| `probe.tcp` from the host (optional) | refused, or accepted and closed at once |

## The fix

- Not published: `ports: ["8080:8080"]` for the service (`docker run -p 8080:8080`), then `docker compose up -d <service>`. On Linux the host can also reach a container directly at its own address, which changes when it restarts.
- Published under another port: connect to `localhost:<host port>`, or change the mapping. The fix names the binding's own address when it doesn't accept the one the client uses (`127.0.0.1:15432` for a client of `192.168.1.10:5432`). A port published with `ports: ["8080"]`, `-p 8080` or `-P` gets a host port Docker picks: whyreach reads it from the running container's actual bindings.
- Published on another address: connect to that address, or publish on every address (`"8080:8080"`).
- A container name from the host: connect to `localhost:<published port>`.

## False positives and limits

- If something on the host itself answers the port (a host process, or docker-proxy for another container), WR019 doesn't fire.
- If several containers listen on the port unpublished, or publish it under another port or address, it can't tell which one is meant: medium, and the explanation lists them.
- A container with `network_mode: host` resolves names the way the host does: a container name used there is this rule's case too.
- **IPv6-only publishing.** A port published on `::` alone (`"[::]:8080:8080"`) is served by Docker's proxy on `[::]` with IPv6 only, which `/proc` can't show; whyreach infers it from the binding. `localhost` is often `127.0.0.1` alone (Ubuntu's `/etc/hosts`), so whyreach uses what the name resolved to on the host, and the fix suggests `[::1]:<port>`.
- A host listener on `0.0.0.0` takes IPv4 only; one on `[::]` takes both families unless it is Docker's IPv6-only proxy.
- From a container, `localhost` is the container: that is WR007, not WR019.

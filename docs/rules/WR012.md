# WR012: a service on the host listens only on 127.0.0.1

- **Layer:** 5, listener
- **Confidence:** high, from the host's listeners alone; a refused connect from the container confirms it
- **Supersedes:** WR001
- **Since:** v0.1 (M2)

## The pitfall

A container reaches the host through a bridge address: `host.docker.internal` with `extra_hosts: ["host.docker.internal:host-gateway"]` points at the default bridge's gateway, `172.17.0.1` (docker0), and a project network has its own gateway. A service on the host that listens on `127.0.0.1` only (PostgreSQL's default `listen_addresses = 'localhost'`, many development servers) accepts connections from the host itself and refuses everything that arrives on a bridge address:

```
psql: error: connection to server at "host.docker.internal" (172.17.0.1), port 5432 failed: Connection refused
```

## The evidence

| Evidence | What it shows |
|---|---|
| `netns.listeners` of the host (`/proc/net/tcp{,6}`) | every listener for the port is on loopback |
| `host.addrs` | the host address the container's connection arrives at, and its interface |
| `docker.container` of the source | the `extra_hosts` mapping that makes the target the host |
| `probe.tcp` from the source (optional) | refused at the bridge address |

The target counts as the host when it is `host.docker.internal` (or another name mapped to `host-gateway`), one of the host's own addresses, or a name that resolved to one. Through MCP, a name with a dot that Docker doesn't know (a LAN host name, say) is looked up only after the user approves it, or under `[probe] names` (`INITIAL.md` §10 Q11): until then whyreach can't tell the target is the host, and WR012 can't fire.

## The fix

Make the service listen on an address containers can reach as well, then restart it:

- the bridge gateway the container uses (`172.17.0.1` for docker0), or
- `0.0.0.0`, and then make sure the host firewall keeps it from the rest of the network.

For PostgreSQL: `listen_addresses = 'localhost,172.17.0.1'`, plus a `host` line for the containers' subnet in `pg_hba.conf`.

## False positives and limits

- Linux Docker Engine only: Docker Desktop forwards `host.docker.internal` to the host its own way, and whether that reaches a loopback-only service hasn't been tested yet, so WR012 doesn't fire there.
- If the loopback listener is a container's port published on `127.0.0.1` (docker-proxy), that is WR006, not a host service.
- From the host itself, loopback works: WR012 is about containers.
- whyreach reads the listeners of its own network namespace, which is the host's when it runs natively, not when it runs as a container (INITIAL.md §3.5).
- A connect from the source that **timed out** or found no route, instead of being refused, contradicts a listener finding: something on the path (a host firewall, say) stops the connection too, and fixing the listener may not be enough. The finding is one level less confident and cites the connect as contradicting evidence.

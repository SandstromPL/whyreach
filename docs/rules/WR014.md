# WR014: `localhost` means IPv4 and IPv6, and the listener takes one family

- **Layer:** 5, listener
- **Confidence:** high when the target leads only to the family the listener lacks (`[::1]` with an IPv4-only listener, or a `localhost` that means `127.0.0.1` alone with an IPv6-only one), so every client fails. Medium when `localhost` means both addresses in the source and only one works: whether the app fails depends on its client, which whyreach can't see. Low when the source's listeners couldn't be read and only the connects show it
- **Probe:** yes. The source's lookup and a connect to each address decide; without probe containers (or root), WR014 isn't evaluated and a gap says how to allow the check
- **Supersedes:** none
- **Since:** v0.2 (M6)
- **Frequency rank:** 18 (`docs/research/failure-signatures.md`)

## The pitfall

`localhost` is two addresses in a container: Docker writes `127.0.0.1 localhost` and `::1 localhost` into every container's `/etc/hosts`, on IPv4-only networks too, and `::1` exists on the container's loopback (measured on Engine 29.9.3). Many hosts do the same (Debian, Fedora, Arch); Ubuntu's `/etc/hosts` maps `localhost` to `127.0.0.1` only.

A server often listens on one family only. `127.0.0.1` and `0.0.0.0` take IPv4 alone; a server told to listen on `localhost` binds the first address it resolves, which is often `::1` alone (measured: Node.js 18 and 24, in a glibc container). A client that tries the other address and gives up gets a refusal from a server that runs:

```
Error: connect ECONNREFUSED ::1:5432          # IPv4-only server, client tried ::1
Error: connect ECONNREFUSED 127.0.0.1:5173    # server on ::1 only, client tried 127.0.0.1
```

Which address a client tries first, and whether it tries the other after a refusal, depends on the client. Measured on Engine 29.9.3 against a server on `127.0.0.1` only, with `localhost` as the target ("—": not measured):

| Client | glibc container, IPv4-only network | glibc container, IPv6 network | musl (Alpine) container |
|---|---|---|---|
| Node.js 18.19 | fails: `ECONNREFUSED ::1` | fails: `ECONNREFUSED ::1` | — |
| Node.js 24.22 (falls back by default: `autoSelectFamily`) | connects to `127.0.0.1` | connects to `127.0.0.1` | — |
| Node.js 24.22 with `--no-network-family-autoselection` | connects: its lookup leaves `::1` out | fails: `ECONNREFUSED ::1` | — |
| Go (`net.Dial`) | tries `::1`, then connects to `127.0.0.1` | — | — |
| Python (`socket.create_connection`) | tries `::1`, then connects to `127.0.0.1` | — | — |
| libpq (`psql`), `redis-cli` | — | — | try `::1`, then `127.0.0.1` |
| busybox `wget` | — | — | fails: tries `[::1]` only |

The order comes from the resolver. musl puts `::1` first: it counts loopback `::1` as IPv6 being configured. glibc puts `::1` first too, except that a lookup with `AI_ADDRCONFIG` (Node.js 24 makes them so, 18 doesn't) leaves `::1` out when the container has no IPv6 address but loopback, as on Docker's default IPv4-only networks. Go's own resolver puts `::1` first. The converse follows: against a server on `::1` only, in a glibc container on an IPv4-only network, Node.js 24.22 fails with `ECONNREFUSED 127.0.0.1` whether it falls back or not, while Node.js 18.19 and Go connect; on an IPv6 network all three connect.

It bites most where `localhost` crosses into a published port: a host whose `localhost` means `::1` too, an app on it using `localhost:5432`, and a database container published on `127.0.0.1` only (`ports: ["127.0.0.1:5432:5432"]`). Docker's proxy then listens on `127.0.0.1:5432` alone, and `[::1]:5432` is refused. It bites inside one network namespace too: an app and a sidecar it shares a namespace with (`network_mode: service:proxy`), or a container reaching its own port.

## The evidence

| Evidence | What it shows |
|---|---|
| the target | `localhost` or another loopback name, or a literal `127.0.0.1` or `[::1]` |
| `probe.dns` from the source | the addresses the name means there: `/etc/hosts` first (whyreach records them IPv4 first, not in the app's order) |
| `netns.listeners` where the connection arrives | the listener's family on the port: in the source's own network namespace (or the one it shares), or on the host for the host and `network_mode: host`. A socket in `/proc/net/tcp` takes IPv4; `[::1]` takes IPv6 alone; `[::]` takes IPv6, and IPv4 too unless it has `IPV6_V6ONLY`, which `/proc` doesn't show |
| `docker.container` of a container publishing the port | on the host, Docker's proxy listens for the binding: the binding's address is the listener's |
| `probe.tcp` from the source, to each address | the address of the family the listener lacks is refused, and the other connects. For a `[::]` listener, the refused IPv4 connect is what shows `IPV6_V6ONLY` |

## The fix

Make the server listen on both families, so every client connects:

- **An IPv4-only server:** listen on `[::]:<port>` instead of `0.0.0.0:<port>` (with `IPV6_V6ONLY` off, the default on Linux, it takes both), or on `[::1]:<port>` as well as `127.0.0.1:<port>` to stay on loopback.
- **A server on `::1` only:** listen on `127.0.0.1:<port>` as well, or on an address that covers both. A server told to listen on `localhost` binds only one of them.
- **A `[::]` server with `IPV6_V6ONLY`:** turn it off, or listen on `0.0.0.0:<port>` too (nginx: `listen <port>;` next to `listen [::]:<port>;`).
- **A port published on loopback:** publish it on both: `ports: ["127.0.0.1:5432:5432", "[::1]:5432:5432"]`, then `docker compose up -d <service>`.

Or connect to the address that works (`127.0.0.1:<port>` or `[::1]:<port>`) instead of `localhost:<port>`. Or use a client that falls back (Node.js 20 and later do by default; `autoSelectFamily: true` on older ones), which helps against an IPv4-only server but not, in a glibc container on an IPv4-only network, against a server on `::1` only: there `::1` isn't among the answers.

## False positives and limits

- **The app's own client isn't visible.** whyreach sees what the name means in the source, the listener and its own connects, not the order the app's resolver returns or whether its client falls back. So when `localhost` means both addresses and one works, WR014 is medium, and the verdict is likely_cause rather than no problem reproduced, although whyreach's connect worked through the other address: an app whose client falls back connects, and then WR014 was harmless. When the target leads only to the missing family, every client fails, and WR014 is high.
- **Only loopback.** A server on `[::]` with `IPV6_V6ONLY` that another container reaches over IPv4 (its address on an IPv4-only network) is refused the same way (ADR 0001 met it by accident), but that isn't about `localhost`: WR014 doesn't judge it, and the diagnosis stays inconclusive.
- **A port published on another host address is WR019's.** From the host, a binding that covers none of the addresses `localhost` means (`ports: ["[::]:8080:8080"]` on a host where `localhost` is `127.0.0.1` alone; the `wr019-ipv6-only` scenario) is WR019's case: the binding's address is the problem. WR014 judges a published port only when a binding covers one of them.
- **Docker Desktop:** on its WSL integration, a published port reaches the WSL2 VM through Docker Desktop's forwarding, which listens nowhere whyreach can read: the VM shows no listener for it, so WR014 doesn't judge it. A container with `network_mode: host` is in Docker Desktop's VM there, whose sockets whyreach can't read, so WR014 doesn't judge it either. A service in the WSL2 VM itself, and containers with their own network namespace (whose listeners come from probe containers there), are judged as on Docker Engine.
- **Without docker-proxy** (`"userland-proxy": false` in the daemon's configuration), the host's listeners don't show published ports, and WR014 doesn't judge them.
- **The listeners must agree.** A listener that takes the refused family, or a refused or closed connect to the family that has a listener, means something else is wrong, and WR014 doesn't fire.
- **IPv6 disabled in a container** (`net.ipv6.conf.all.disable_ipv6=1`): Docker leaves `::1` out of its `/etc/hosts` then, so `localhost` means `127.0.0.1` alone, and a connect to `[::1]` fails with "cannot assign requested address". WR014 only judges refusals.
- **A name that resolves to loopback through DNS** (rather than `/etc/hosts`): whyreach reads the source's listeners only for targets it knows are loopback before the probe runs (`localhost`, a literal address, an `extra_hosts` entry), so for such a name only the connects show it, at low confidence.

# WR016: a timeout means a silent drop

- **Layer:** 4, path
- **Confidence:** high when Docker's metadata names the dropper: the network the source and the destination share disables inter-container communication. Medium when a container on a network the source shares (or the host itself) holds the address, and its listening sockets show it would have answered: a listener that takes the connect with an empty accept queue, or none at all, so its kernel would have refused. Low otherwise: an address outside Docker, the host connecting to a container, listening sockets that couldn't be read, or a listener whose accept queue holds connections already (the app may have stopped accepting)
- **Probe:** yes. Without the source's connect through the target's name or address, WR016 isn't evaluated, and the probe's gap says how to allow it
- **Supersedes:** nothing. It is the last resort for timeouts: WR004, WR005, WR008, WR009, WR011, WR013, WR015 and WR024 supersede it, and WR021 will
- **Since:** v0.2 (M6)
- **Frequency rank:** not measured (`docs/research/failure-signatures.md`: generic timeouts show up inside other failures)

## The pitfall

A connect that gets no answer at all, neither an accept nor a refusal, means something dropped the packets on the way, without a word. A destination that exists answers: its kernel accepts the connection when something listens, and refuses it when nothing does. A firewall or router that rejects sends a reset or an ICMP error ("no route to host", "network is unreachable"). Only a drop, or a listener whose accept queue is full, leaves the client waiting until it gives up:

```
$ nc -vz -w 2 api 8080
nc: connect to api port 8080 (tcp) timed out: Operation now in progress
```

Measured in M6 (ADR 0002's amendment), in a network namespace of made-up addresses and on Engine 29.9.3:

| What stops the connect | What the client gets |
|---|---|
| a firewall rule that drops, on the destination's side (INPUT) or on the source's (OUTPUT) | a timeout |
| a rule on the destination's side that drops the reply (a route to nowhere) | a timeout |
| a listener whose accept queue is full: the app doesn't accept | a timeout |
| a Docker network with `com.docker.network.bridge.enable_icc: "false"`, between two of its containers | a timeout, though the destination listens |
| a firewall rule that rejects with `icmp-host-prohibited`, `admin-prohibited` or `host-unreachable` | "no route to host" (EHOSTUNREACH) at once |
| a firewall rule that rejects with `net-prohibited` | "network is unreachable" (ENETUNREACH) at once |
| a firewall rule that rejects with `tcp-reset` or `port-unreachable` | "connection refused" at once, like nothing listening |
| on the source's side, a route of type `prohibit`, `blackhole` or `unreachable`, or no route at all | EACCES, EINVAL, EHOSTUNREACH or ENETUNREACH, at once |
| an address on the local network that nothing holds (ARP gets no answer) | EHOSTUNREACH after about 3 s, so whyreach's 2 s connect times out first |

The fourth row is Docker's own silent drop: the option tells Docker to drop the traffic between the network's containers, while each still reaches the host and Docker's DNS.

## Which rule takes which error

whyreach keeps refused, timeout and unreachable apart, and the error decides which rules may explain it:

| The source's connect | Rules |
|---|---|
| timed out | WR016, unless a rule that explains the timeout supersedes it: WR004 (a container on a network the source isn't on), WR008 (a stopped container's address), WR013 (a Docker subnet took the address's route), WR015 (an internal network), WR024 (an address on the source's own network that no container holds); WR021 for the host, once built |
| "no route to host" (EHOSTUNREACH) | WR024 and WR013 on a Docker subnet, WR015; WR021 when the address is the host's, once built. Never WR016: it is an answer |
| "network is unreachable" (ENETUNREACH) | WR015 (an internal network has no way out); otherwise no rule yet |
| EACCES or EINVAL (a `prohibit` or `blackhole` route), or EPERM | none: the source's own kernel refused to send |
| refused | the listener rules (WR001, WR002, WR003, WR012, WR019 and others) |

## The evidence

| Evidence | What it shows |
|---|---|
| `probe.tcp` from the source | every connect through the target's name or literal address timed out (whyreach gives up after 2 s); a connect to an address from Docker's metadata doesn't count, since it isn't how the app connects |
| `docker.container` of the destination | a running container that holds the address, on a network the source shares (or the host's own address); the attachment carries the network's `com.docker.network.bridge.enable_icc` option, from Docker's network list |
| `netns.listeners` of the destination, or of the host | a listener that takes the connect, with the length of its accept queue (`rx_queue` in `/proc/net/tcp`), or none: either way the destination would have answered, unless connections are waiting in the queue |
| `host.route` for an address outside Docker | the route the host picks for it (the default one included) and the other routes that cover it: where the traffic goes before something drops it |

The route is looked up only for an address outside every Docker network's subnet that the source's connect timed out on, and only where Docker Engine runs on this machine. From a container, the traffic leaves through its network's gateway, so the host's routing table and firewall decide the rest of the way.

## The fix

- **The network disables inter-container communication** (high). If the containers are meant to talk, delete `com.docker.network.bridge.enable_icc` from the network's `driver_opts` in the Compose file and recreate it (`docker compose down`, then `docker compose up -d`), or put both containers on another network together. On the default bridge, the daemon's `"icc": false` in `/etc/docker/daemon.json` does it. If the isolation is on purpose, publish the port and connect through the host.
- **A drop between two containers** (medium). Look for firewall rules in either container's network namespace (a VPN client's kill switch drops what it doesn't expect), the host's `DOCKER-USER` chain (`sudo iptables -S DOCKER-USER`), and the network's options (`docker network inspect`).
- **A drop on the way to the host** (medium). Most often the host's firewall (ufw, firewalld or iptables INPUT rules), which by default doesn't let Docker's networks in: allow the port from the containers' subnet, for example `sudo ufw allow from 172.22.0.0/16 to any port 5432 proto tcp`.
- **A full accept queue** (low). The app has stopped accepting connections (stuck, or every worker busy): check its logs, and restart it.
- **An address outside Docker** (low). Check from the host whether it answers (`nc -vz -w 3 ADDR PORT`). A private address that only the host's default route covers usually means the route to it is missing (a VPN that is down). If the host reaches it and the container doesn't, Docker's forwarding is in the way: `ip_forward`, or the firewall's FORWARD policy.

## False positives and limits

- **The last resort.** A timeout that another rule explains is that rule's: WR016 is suppressed and stays in the diagnosis's `suppressed` list. A connect through the target's name that never happened (the name didn't resolve) gives WR016 nothing to judge.
- **WR026, later.** The high case, a network that disables inter-container communication, moves to WR026 once it is built (planned after v0.2's six rules): Docker's network options alone settle it, before any connect.
- **Only timeouts.** "No route to host" and "network is unreachable" are answers. ARP giving up on an address nothing holds takes about 3 s, longer than whyreach's connect, so it shows as a timeout, which WR024 or WR013 explains.
- **A full accept queue looks like a drop.** While the queue is full, the kernel drops new connections silently. The listener's queue shows the waiting connections, and WR016 then says so, at low. `/proc/net/tcp` shows the queue's length but not its limit, and a queue that fills only after the listeners were read goes unseen.
- **The dropper is rarely named.** whyreach parses no firewall rules (out of scope, `INITIAL.md`). Docker's own option is in its metadata; any other drop stays unnamed (medium), and a VPN container's kill switch looks the same as a `DOCKER-USER` rule.
- **The host's firewall** is WR021's case (v0.2, next): container-to-host traffic that the host's firewall rejects (EHOSTUNREACH) or drops (a timeout), with a listener on the host. Until it is built, WR016 judges the timeouts, at medium; WR021 will supersede it.
- **From the host to a container**, nothing of Docker's stands in the way on a bridge network, so the drop is in the container's own namespace, or the network is a macvlan or ipvlan one, whose containers the host can't reach by design. whyreach doesn't record a network's driver on the attachment, so this stays low.
- **Docker Desktop.** Traffic between containers, or to an address on the source's own network, stays in Docker Desktop's VM, where Docker's rules are the same, and WR016 judges it as on Engine. Traffic that leaves the VM (to the host, `host.docker.internal`, a published port reached from the WSL2 distro, or an address outside Docker) goes through Docker Desktop's own network stack, which whyreach can't see: WR016 doesn't fire there rather than guess.
- **Forwarded traffic** is looked up as the host's own traffic: a routing rule that matches a container's source address could send it elsewhere (as for WR013).
- **IPv6-only listeners** (`[::]` with `IPV6_V6ONLY`) can't be told from dual-stack ones in `/proc`: a `[::]` listener counts as taking an IPv4 connect.
- **Privacy:** the route record keeps the chosen route and the routes that cover the address, each with its prefix, interface and table only. In a redacted report, the ranges and interfaces of routes that aren't Docker's get pseudonyms, as for WR013.
- **The lab's scenario** (`wr016-silent-drop`) is the high case, a network with inter-container communication disabled. A drop that whyreach can't name needs a firewall rule in a container (`NET_ADMIN` and an image with iptables, which the lab doesn't pull) or one on the host: fixtures, engine tests and the measurements in a network namespace cover it.

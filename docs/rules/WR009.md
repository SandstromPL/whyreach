# WR009: the containers share only Docker's default bridge network

- **Layer:** 3, naming
- **Confidence:** high, from the network name alone
- **Supersedes:** WR005, WR016
- **Since:** v0.1 (M2)

## The pitfall

Containers started with plain `docker run` (or Compose services with `network_mode: bridge`) are on Docker's default `bridge` network. It has no embedded DNS: container names and service names resolve only on **user-defined** networks. The containers can reach each other by address, but not by name:

```
ping: bad address 'api'
Name or service not known
```

## The evidence

| Evidence | What it shows |
|---|---|
| `docker.container` of both containers | the only network they share is `bridge`, and the name resolves on none of their shared networks. When they share a user-defined network too, Docker's DNS works there but doesn't know the name (an alias on another network): that is WR005, not WR009 |
| `probe.dns` from the source (optional) | the name did not resolve (the default bridge uses the host's upstream DNS directly) |

## The fix

Put both containers on a user-defined network:

```sh
docker network create app
docker network connect app <api container>
docker network connect app <worker container>
```

In Compose, remove `network_mode: bridge`: services then share the project's own network, where names resolve.

## False positives and limits

- A legacy `--link` writes the name into `/etc/hosts`: WR009 doesn't fire for a linked name.
- If the containers also share a user-defined network where the name resolves, WR009 doesn't fire.
- If they share no network at all, that is WR004.
- Connecting by the default-bridge address works, but it changes when the container restarts.

# WR007: `localhost` used inside a container

- **Layer:** 2, addressing
- **Confidence:** high when the source's own listeners can be read; medium otherwise
- **Supersedes:** WR001
- **Since:** v0.1 (M1)
- **Frequency rank:** 1 (`docs/research/failure-signatures.md`)

## The pitfall

Inside a container, `localhost`, `127.0.0.1` and `::1` are the container's own network namespace, not the host's and not another container's. Code that worked on a laptop with `DATABASE_URL=postgres://localhost:5432/app` stops working once the app runs in a container: the connection goes to the app's own container, where nothing listens on 5432, and is refused.

```yaml
services:
  db:
    image: postgres
  worker:
    environment:
      DATABASE_URL: postgres://localhost:5432/app   # worker itself, not db
```

## The evidence

| Evidence | What it shows |
|---|---|
| the target | `localhost`, `*.localhost`, `127.0.0.0/8`, `::1` or `0.0.0.0` |
| `docker.container` of the source | the source has its own network namespace (not `network_mode: host`) |
| `netns.listeners` of the source | nothing in the source accepts connections to the port on loopback. This settles the cause |
| `netns.listeners` of the other containers on the source's networks | which container serves the port: it chooses the fix |
| `netns.listeners` of the host | whether a host service serves the port: it chooses the other fix |
| `probe.tcp` from the source (optional) | the connect to localhost is refused: confirms it |

## The fix

It depends on where the service runs:

- **Another container on a shared network:** use its Compose service name, for example `api:8080` or `db:5432`. The name resolves through Docker's embedded DNS on the shared network.
- **The host:** use `host.docker.internal:8080`. On Docker Engine (Linux) this name exists only with `extra_hosts: ["host.docker.internal:host-gateway"]` on the source (WR011), and the host service must listen on an address containers can reach, not only on `127.0.0.1` (WR012).

## False positives and limits

- If something in the source itself listens on the port (on loopback or on all interfaces), `localhost` reaches it and WR007 does not fire.
- If a connect from the source to `localhost` succeeds, WR007 does not fire.
- With `network_mode: host`, `localhost` is the host, and WR007 does not fire.
- With `network_mode: container:X`, `localhost` is X's network namespace: X's listeners decide. When they can't be read (Docker Desktop without probe containers, say), WR007 doesn't fire: in a sidecar setup `localhost` is meant to reach X, which may well serve the port (since v0.2, M6).
- When the source's own listeners can't be read, WR007 still fires with medium confidence, because the pattern is by far the most common one.
- **A name can mean loopback too.** When the source's `extra_hosts` map the target name to `127.0.0.1` or `::1` (`db:127.0.0.1`), or the name resolves to loopback in the source (a DNS name such as `localtest.me`, which points at 127.0.0.1), the name is the source itself: WR007 fires the same way, and the fix for `extra_hosts` is to remove the entry, so that Docker's DNS answers the name again.
- Through MCP, a lookup of such a name with a dot waits for the user's approval of the name, or for `[probe] names` to cover it (`INITIAL.md` §10 Q11): until then whyreach can't see that the name means loopback, and WR007 doesn't fire. `localhost` and `*.localhost` are loopback targets from the start, and `extra_hosts` mappings need no lookup.

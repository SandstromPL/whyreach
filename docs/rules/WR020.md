# WR020: the container's upstream DNS server doesn't answer

- **Layer:** 3, naming
- **Confidence:** high when the lookup times out (or can't reach the resolver) at Docker's embedded DNS while the source's own name resolves there; medium without that control, when the control fails too, or off Docker's DNS (the default bridge); a SERVFAIL on a dotted name is one level lower than a timeout in each case (low unless the control resolved)
- **Probe:** a lookup from inside the source is needed (Probe? yes): through a probe container, or, when whyreach runs as root, by entering the source's network namespace (the netns executor, M3). Without either the rule isn't evaluated, and the gap says how to enable probe containers. Through MCP, the lookup of an outside name also needs the user's approval or `[probe] names` (see below)
- **Supersedes:** nothing
- **Since:** v0.1 (M2)

## The pitfall

Inside a container on a user-defined network, `/etc/resolv.conf` points at Docker's embedded DNS, `127.0.0.11`. It answers the names it knows itself (containers, Compose services, aliases) and forwards everything else to upstream servers: the host's resolvers, or the ones set with `dns:` in Compose or `"dns"` in `/etc/docker/daemon.json`. Docker records them in a comment in the container's `resolv.conf`:

```
nameserver 127.0.0.11
# ExtServers: [192.0.2.53]
```

When those upstream servers don't answer (a VPN changed the host's DNS, a corporate firewall blocks them, a `dns:` setting points at a dead address), internal names still resolve while external ones time out:

```
getaddrinfo EAI_AGAIN api.github.com
Temporary failure in name resolution
```

## The evidence

| Evidence | What it shows |
|---|---|
| `probe.dns` of the target, from the source | the lookup timed out (every query), couldn't reach the resolver at all, or failed with SERVFAIL, at `127.0.0.11:53`, with the upstream servers from `# ExtServers:` |
| `probe.dns` of the source's own container name (a control) | it resolved at once through the same server: Docker's DNS works |
| `docker.container` of the source | its own `dns:` setting (`HostConfig.Dns`), for the fix |

The control lookup never leaves the host: Docker's DNS answers it itself. The rule never fires on NXDOMAIN, which means the upstream answered, or on a single-label name's SERVFAIL, which is what a systemd-resolved stub answers for names it won't forward (WR005's case).

## The fix

- If the container sets its own resolver (`dns:` in Compose, `--dns`): point it at one that works from containers, or remove it, then recreate the container.
- If Docker forwards to the host's systemd-resolved stub (`ExtServers: [host(127.0.0.53)]`): the host's own DNS is failing. Check `resolvectl status` (VPN changes are a common cause), then restart Docker.
- Otherwise set `dns: [<a resolver that works>]` for the service, or `"dns"` in `/etc/docker/daemon.json` for every container, and recreate it.

## False positives and limits

- SERVFAIL for a multi-label name can also come from that domain's own servers (a DNSSEC failure, say), so it is one level less confident than a timeout.
- If even the control lookup fails, Docker's embedded DNS itself may be broken, not only its upstream: confidence drops one level and the explanation says so.
- On the default bridge there is no embedded DNS: the container uses the upstream server directly, there is no internal name to compare with, and the finding is medium (low with a SERVFAIL).
- On networks with `internal: true` only, Docker's DNS doesn't forward to the upstream servers: it answers SERVFAIL at once (measured on Engine 29.9.3). That is the network's isolation (WR015, v0.2), not a failing upstream, so WR020 doesn't fire. whyreach reads the flag from Docker's network list.
- If no outbound traffic leaves the containers at all (no NAT or forwarding, WR022 in v0.3), DNS times out too. whyreach doesn't probe public addresses by default (the `[probe] allow` list), so it can't tell these apart yet.
- **Through MCP, the lookup needs the user's approval.** The name this rule looks up is usually outside Docker, such as `example.com`. For an MCP client, whyreach sends that lookup only after the user approves the exact name when whyreach asks, or when `[probe] names` lists its domain (`INITIAL.md` §10 Q11). Until then WR020 can't fire, since it has no lookup of the name to judge, and the gap names the setting. Headless agents, which can't be asked, need the domains they diagnose listed. The CLI looks up any name.
- A nameserver on the probe block list (link-local or cloud-metadata addresses) gets no query. When it is the first, the one the app asks, whyreach makes no lookup, and WR020 can't fire: some clouds serve DNS at 169.254.169.254 (`INITIAL.md` §10 Q13). When a later one is blocked, whyreach asks only those before it; if they fail, the app would ask the blocked one next, so the lookup is refused (a gap), not reported as "does not resolve".

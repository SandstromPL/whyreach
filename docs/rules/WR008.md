# WR008: the destination is not running, is restarting, or is unhealthy

- **Layer:** 1, destination
- **Confidence:** high when the container is stopped, restarting or paused; medium when it runs but is unhealthy or crash-looping
- **Supersedes:** WR001, WR005, WR016
- **Since:** v0.1 (M1); a stopped container's fixed address since v0.2 (M6)

## The pitfall

Whatever the network looks like, nothing can connect to a container that isn't running. A container that exited, crashed or is caught in a restart loop has **no network address**: Docker releases it when the container stops. Its name then fails to resolve and its old address times out, which looks like a naming or a path problem.

A container with a fixed address (Compose `ipv4_address` or `ipv6_address`, `docker run --ip`) keeps that setting while it is stopped, and gets the address back when it starts. So a connection to that address, given literally or through the source's `extra_hosts`, is about that container too, and WR008 names it.

whyreach checks container state **before any probe**: a restarting container can't even be joined by a probe container (`cannot join network namespace of a non running container`), and has no process whose namespace the netns executor could enter. When every container the name refers to on the source's networks is stopped, no probe runs, and none is asked for.

## The evidence

| Evidence | What it shows |
|---|---|
| `docker.container` of the destination | `State` (`exited`, `restarting`, `paused`, `created`, `dead`), `ExitCode`, `RestartCount`, health status, and `StartedAt` compared with when it was inspected |
| the container list and `docker.container` of the destination, for an address target | its fixed address on a network (`fixed_ipv4`, `fixed_ipv6`, from its endpoint's `IPAMConfig`), when no container that is running or paused holds the address |

| State | Confidence |
|---|---|
| exited, created, dead, removing | high |
| restarting | high |
| paused | high |
| running, but the healthcheck reports `unhealthy` | medium |
| running, but restarted at least 3 times and started less than 30 s before the inspect (a crash loop caught between restarts) | medium |

## The fix

- **Stopped:** start it (`docker compose up -d <service>`) and find out why it stopped: `docker logs <container>`.
- **Restarting:** read its logs and fix what makes it exit; a restart policy only hides the crash.
- **Paused:** `docker unpause <container>`.
- **Unhealthy:** check the healthcheck and the logs. The app may still be starting (see WR010), or failing.

## False positives and limits

- If the name matches several containers (replicas) and at least one is running and healthy, WR008 does not fire: Docker's DNS sends traffic to the running ones.
- If the only stopped match is on no network the source is on (another Compose project, say), it may not be the container the source means: WR008 is one level less confident, and it doesn't fire at all when the name resolves or connects from the source. Such a match doesn't stop the probes either.
- A container that publishes the port where the target arrives on the host (`localhost:18080` from the host, `host.docker.internal:18080` from a container) is the destination for certain, wherever its networks are: WR008 keeps its confidence. It still reports a paused container whose connect succeeds, as "also found": docker-proxy and the paused container's kernel complete the TCP handshake, but nothing answers.
- If the source's `extra_hosts` map the name, `/etc/hosts` answers first and a container with that name is irrelevant.
- If the name matches no container at all, that is WR005, not WR008.
- **An address target matches a stopped container only through its fixed address.** Docker clears a dynamic address when the container stops and keeps nothing that says what it was, so a connection to it is WR024's (a stale address). Docker also hands a stopped container's fixed address to other containers (measured on Engine 29.9.3): when one that is running or paused holds it, the connection goes there, and that container is the destination. The stopped one would then fail to start, with "Address already in use".
- "Unhealthy" is a weaker signal than "not running": the app may accept connections and still fail its healthcheck, so it is medium confidence.
- The source container's own state is not WR008's concern: if the source isn't running, whyreach reports that it can't probe from it.

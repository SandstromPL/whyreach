# WR004: the two containers share no network

- **Layer:** 3, naming
- **Confidence:** high from Docker metadata alone; the probe container adds confirmation
- **Supersedes:** WR005, WR016
- **Since:** v0.1 (M1)
- **Frequency rank:** 2 (`docs/research/failure-signatures.md`)

## The pitfall

Containers reach each other only over a network they are both attached to. The most common way to end up without one is two Compose projects: every project gets its own `<project>_default` network, so `worker` in one project can't see `api` in another, even though both are running on the same machine.

```
~/src/api      $ docker compose up -d   # project "api",    network api_default
~/src/worker   $ docker compose up -d   # project "worker", network worker_default
```

Across networks, the service name doesn't resolve (Docker's embedded DNS only answers for its own network) and traffic is silently dropped, so connecting by address **times out** rather than being refused.

## The evidence

| Evidence | What it shows |
|---|---|
| `docker.container` of the source | the networks the source is attached to (or, for `network_mode: container:X`, X's) |
| `docker.container` of the destination | the target name matches its container name, Compose service, alias or DNSNames, or the target address is one of its addresses, but only on networks the source is not on |
| `probe.dns` from the source (optional) | the name does not resolve. The rcode depends on the host's resolver (SERVFAIL behind systemd-resolved, NXDOMAIN elsewhere), so it is recorded but never decides anything |
| `probe.tcp` from the source (optional) | a connect to the destination's own address times out |

## The fix

Put both containers on a shared network. With Compose, declare the other project's network as external in the source's file:

```yaml
services:
  worker:
    networks: [default, api_default]
networks:
  api_default:
    external: true
```

Or run both services in one Compose project. To test without editing files: `docker network connect api_default <worker container>` (this changes the running container until it is recreated).

## False positives and limits

- If the name resolves from the source to an address that is **not** the destination's (for example a LAN host found through the host's DNS search domain), the confidence drops one level: the user may mean that other host.
- If a connect through the name succeeds, WR004 does not fire.
- A source with `network_mode: host` or `none` has no Docker networks to share; WR004 does not fire for it.
- If the name matches no container anywhere, that is WR005 (a mistyped name), not WR004.
- When the name matches containers in several projects, the one in the source's own Compose project is preferred, then the rest by name; the explanation lists them all.
- The timeout seen when connecting by address is a consequence of WR004, so WR004 suppresses WR016.

# WR013: a Docker subnet overlaps a VPN or LAN route

- **Layer:** 4, path
- **Confidence:** high when a route that isn't Docker's (a VPN's, a LAN's; not a default route) also covers the address. Medium without one: the address lies in a Docker network's subnet, no container holds it, and nothing else on the host claims it. One level lower when some containers' metadata couldn't be read, since one of them might hold the address
- **Probe:** no. The host's route lookup decides, with no probe container and no root; a connect from the source that something answers (accepted or refused) rules it out, and one that gets no answer is cited
- **Supersedes:** WR016, WR024
- **Since:** v0.2 (M6)
- **Frequency rank:** 15 (`docs/research/failure-signatures.md`)

## The pitfall

Docker gives each bridge network a subnet, from its default pools (`172.17.0.0/16`, `172.18.0.0/16` and on, `192.168.0.0/20`s) or from the Compose file, and adds a route into the network's bridge on the host. When a VPN or the LAN uses the same range, the kernel picks one route per address: the most specific, and at equal length Docker's (metric 0). Traffic meant for a machine behind the VPN then goes into Docker's bridge, where nothing answers:

```
$ ip route get fibmatch 10.8.1.5
10.8.1.0/24 dev br-1a2b3c4d5e6f proto kernel scope link src 10.8.1.1
$ ip route show table all match 10.8.1.5
10.8.0.0/16 dev tun0 scope link
10.8.1.0/24 dev br-1a2b3c4d5e6f proto kernel scope link src 10.8.1.1
```

It bites three ways (measured on Engine 29.9.3 and in a network namespace of made-up routes; ADR 0002's M6 amendment):

- **From the host:** the host's routing table sends the address into the bridge. With no container there, the connect fails with "no route to host" once ARP gives up (about 3 s), so whyreach's 2 s connect times out.
- **From a container on another network:** its traffic leaves through its gateway to the host, whose routing table sends it into the other network's bridge, and Docker drops traffic between its networks: a timeout.
- **From a container on that network:** the address is on its own subnet, so it sends it straight onto the bridge, whatever the host's routes say.

## The evidence

| Evidence | What it shows |
|---|---|
| `host.route` for the target's address | the routing table entry the kernel picks for it (netlink RTM_GETROUTE with `RTM_F_FIB_MATCH`, as `ip route get fibmatch`), every unicast route in any table that covers it (each with its prefix, interface and table only; default routes are left out, as they cover every address), and the Docker bridge networks whose subnets hold it, with their bridges (from Docker's network list) |
| the container list and `docker.container` records | no container holds the address, running or as a stopped container's fixed address |
| `docker.container` of the source | whether the address is on the source's own network, and that the source isn't only on `internal: true` networks |
| `probe.tcp` from the source (optional) | no answer (a timeout, or "no route to host") |

whyreach looks routes up only for the target's addresses that lie in a Docker bridge network's subnet, aren't that network's gateway, and that no container holds: the literal address, the one the source's `extra_hosts` map the name to, or what the source's lookup gave.

## The fix

Move the Docker network to a range that none of your VPN or LAN routes use:

- **A Compose network:** set its subnet in the Compose file (`networks: <name>: ipam: config: [{subnet: <free range>}]`), then recreate it: `docker compose down`, then `docker compose up -d`.
- **A network made with `docker network create`:** remove it once its containers are gone, and create it again with `--subnet <free range>`.
- **Docker's default bridge (`docker0`):** set `bip` in `/etc/docker/daemon.json`, and restart Docker.

To keep Docker from picking such a range again, set `default-address-pools` in `/etc/docker/daemon.json` to ranges your VPN and LAN don't use, and restart Docker. Without a competing route (medium), the address may also be a container's that is gone: then connect by the container's name.

## False positives and limits

- **Only this direction.** A VPN route more specific than a Docker subnet, or a routing rule that sends a range to a VPN's own table ahead of the main one, takes host-to-container traffic away from the bridge for the containers in that range. whyreach doesn't look the routes of containers' own addresses up, so WR013 doesn't judge it.
- **A VPN client inside a container** (`network_mode: service:vpn`, a common pattern): its routes are in the container's network namespace, not the host's, and WR013 doesn't read them.
- **Forwarded traffic:** whyreach looks a route up as the host's own traffic would. A routing rule that matches a container's source address or interface could send the forwarded traffic elsewhere.
- **A default route** (or the two `/1` halves VPN clients add) covers every address, so it isn't a competing route: it says nothing about whose range the address is in.
- **An address on the source's own network** with no competing route is WR024's: a stale or hard-coded container address. With a competing route, the route shows the address is meant to be a machine behind the VPN or LAN, and WR013 supersedes WR024.
- **Other drivers:** a macvlan or ipvlan network shares the LAN's range on purpose, and has no bridge of the host's: WR013 doesn't judge it.
- **Docker Desktop** routes its containers' traffic inside its own VM, so the routes of the machine whyreach runs on (the WSL2 VM, on Windows) say nothing about Docker's networks: the route record is a gap, and its advice says how to compare the subnets with the VPN's routes by hand. In whyreach's image without `--network host`, the host's routes are out of sight too: a gap.
- **Docker refusing to create a network** ("could not find an available, non-overlapping IPv4 address pool") isn't a connection failure, and whyreach doesn't diagnose it; `default-address-pools` is its fix too.
- **Privacy:** the record keeps only the routes that cover the address, and of each its prefix, interface and table: no gateway, source address or metric. In a redacted report, the ranges and interfaces of routes that aren't Docker's, and the host's own addresses on those interfaces, get pseudonyms even where private addresses are kept (an interface named by a plain word, such as `lan`, keeps its name).
- **The lab can't make a competing route** without changing the host's routes. Its scenario is the medium case (an address in a lab network's subnet that no container holds); the high case is covered by fixtures, engine tests and the route lookup's test against made-up routes in an unprivileged network namespace.

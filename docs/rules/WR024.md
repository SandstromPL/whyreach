# WR024: a stale or hard-coded container address

- **Layer:** 2, addressing
- **Confidence:** medium from Docker metadata alone: the target is an address on one of the source's networks, and no container holds it. High when a connect from the source got no answer ("no route to host", or whyreach's own timeout first). One level lower when some containers' metadata couldn't be read or Docker's list of containers couldn't be read (one of them might hold the address), and when the connect found "network is unreachable" instead
- **Probe:** partly. A connect from the source confirms it; one that is refused or accepted means something holds the address, and WR024 doesn't fire
- **Supersedes:** WR016
- **Since:** v0.2 (M6)
- **Not built yet:** the catalog row's second half, an app whose sockets still point at an old address (see the limits)

## The pitfall

Docker hands out a container's addresses when it starts. Recreate the container (`docker compose up` after a change, a new image, `docker compose down` and `up`) and it can come back with another address. An address written into configuration then points at nothing:

```
DB_HOST=172.18.0.3          # what docker inspect said last week
connect: no route to host
dial tcp 172.18.0.3:5432: i/o timeout
```

The same happens with an `extra_hosts` entry that maps a service's name to its address: `/etc/hosts` answers before Docker's DNS, so the name keeps pointing at the old address.

Nothing answers at an address no container holds. The kernel asks the network who has it (ARP for IPv4), gets no answer, and fails the connect with "no route to host" (EHOSTUNREACH) after about 3 s, on normal and `internal: true` networks alike (measured on Engine 29.9.3; rule experiments, E8). whyreach's own connect gives up after 2 s, so it usually reports a timeout instead, unless something in the container is already retrying that address.

## The evidence

| Evidence | What it shows |
|---|---|
| `docker.container` of the source (for `network_mode: container:X`, of X) | the networks it is on, with each network's subnets and gateway addresses (from Docker's network list) |
| the target | an address on one of those subnets, given literally or through the source's `extra_hosts`; not the network's gateway, which is the bridge's own side (the host's, or Docker Desktop's VM's) |
| the container list, and `docker.container` of the containers on that network | no container holds the address, and none has it as its fixed address; the finding names the ones there now, with their addresses |
| `probe.tcp` from the source (optional) | the connect got no answer: `EHOSTUNREACH`, or a timeout |

## The fix

Connect by name, not by address: Docker's DNS on a user-defined network answers a service's name (its Compose service, container name or alias) with the address it has now. Replace the address in the source's configuration with the name of the service that held it, for example `db:5432` instead of `172.18.0.3:5432`, then recreate the source (`docker compose up -d <service>`) so it reads it again.

For an `extra_hosts` entry, remove it: Docker's DNS then answers the name with the current address.

On Docker's default `bridge` network names don't resolve, which is why addresses get written down there. Put the containers on a user-defined network (Compose gives every project one) and connect by name.

## False positives and limits

- **An app that looked a name up once.** Many apps resolve a name when they start and keep the address: nginx does for a static `proxy_pass` upstream, until it is reloaded. After the destination is recreated with a new address, the app still connects to the old one, while whyreach, which looks the name up afresh, finds nothing wrong. Telling them apart needs the source's open connections (sockets in SYN-SENT to an address no container holds; measured: an app retrying such an address shows one most of the time). That half of the catalog row is not built yet, and needs the source's connection table read on every platform: from `/proc/<pid>/net/tcp` on Docker Engine, inside a probe container on Docker Desktop, keeping only addresses and ports.
- **An address on another network's subnet,** or on no Docker network at all (the network itself was recreated with another subnet): WR024 judges only the source's own subnets. A connect to another Docker network is dropped silently, held address or not (WR004's case), and an address outside Docker could be any host.
- **A stopped container's fixed address** (Compose `ipv4_address` or `ipv6_address`) is that container's: Docker keeps the setting while the container is stopped, whyreach matches the address to it, and WR008 says to start it. A dynamic address isn't kept once its container stops, so when the target was a stopped container's dynamic address, WR024 fires: nothing says whose address it was. The finding lists the stopped containers on the network, and the fix says to start the one whose address it was.
- **Something outside Docker's knowledge on the bridge** (an interface attached by hand) would answer: a connect that is refused or accepted shows it, and WR024 doesn't fire.
- **The network's gateway** is the bridge's own side: on Docker Engine an address of the host's (WR001 or WR012 apply there), on Docker Desktop one of its VM's. WR024 never fires for it, on internal networks either, where Docker gives the container no gateway but the network list names one.
- **When Docker's network list can't be read,** the subnets are unknown and WR024 doesn't fire.
- **Docker Desktop:** whyreach decides from Docker's metadata, which describes Docker Desktop's VM, so WR024 doesn't depend on the platform; containers there sit on the same kind of Linux bridge. The WSL2 lab's run B (`docs/wsl2-lab.md`) checks it on Windows.

# WR005: no container on the source's networks has that name

- **Layer:** 3, naming
- **Confidence:** high when the lookup from the source fails too (not by timing out); medium from metadata alone; for a name no container has, one level lower when some containers' metadata couldn't be read or was skipped (Probe? partly)
- **Supersedes:** WR016
- **Since:** v0.1 (M2)

## The pitfall

The name the client uses matches no container name, Compose service or alias on any network it is on: a typo (`apii`), a renamed service, a service that isn't started, or an alias declared on another network.

```
nginx: [emerg] host not found in upstream "apii"
could not translate host name "dbb" to address
```

## The evidence

| Evidence | What it shows |
|---|---|
| `docker.container` of the source and of every container on its networks | the names Docker's DNS answers there: container names, services, aliases and DNSNames |
| `probe.dns` of the name, from the source (optional) | it did not resolve |
| `probe.dns` of the source's own name (a control) | Docker's DNS answers names it knows |

The rule decides from Docker metadata, never from the DNS reply code: unknown names come back SERVFAIL behind a systemd-resolved stub and NXDOMAIN elsewhere (rule experiments, E1 and E2). The reply only confirms.

It suggests the closest name by edit distance (one edit for names up to 3 characters, two up to 8, three beyond), services first.

## The fix

Use the suggested name, or a service on the source's network. If the name is meant to be another service: start it, or give a service that alias. The fix names the network by its Compose key (`default` for the network Docker calls `shop_default`):

```yaml
services:
  api:
    networks:
      default:
        aliases: [apii]
```

## False positives and limits

- If the name matches a container on another network, that is WR004; on the default bridge only, WR009.
- **An alias declared on another network.** Aliases are per network: a container that shares a network with the source but has the alias only on a network the source isn't on doesn't answer to it on the shared one. WR005 says so, and suggests the container's name on the shared network or the alias there too (`networks: {<key>: {aliases: [db]}}`).
- A lookup that **timed out** says the upstream resolver didn't answer (WR020), not that Docker doesn't know the name: WR005 stays medium, and WR020, when it fires high, comes first.
- A name with a dot and no close container name is treated as an external name: not WR005 (WR020 covers its DNS failures).
- Through MCP, the confirming lookup of a name with a dot that no container answers to waits for the user's approval of that name, or for `[probe] names` to cover it (`INITIAL.md` §10 Q11). Until then WR005 stays medium, decided from metadata alone. Names without a dot, such as a mistyped service name, are looked up as usual.
- If the name resolves from the source (a search domain, `/etc/hosts`), it doesn't fire.
- If some containers' metadata couldn't be read, or more than 64 containers share the source's networks (whyreach inspects the first 64 and records the rest as skipped, code `limit`), one of the others might carry the name as an alias: confidence drops one level. (Known issue: the finding for an alias on another network isn't lowered yet.)
- A source on the default bridge only can't resolve any name: no WR005.

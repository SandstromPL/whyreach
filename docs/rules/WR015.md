# WR015: the container is only on internal networks, and the target is outside them

- **Layer:** 4, path
- **Confidence:** high from Docker metadata alone: the networks' `internal: true` flags and subnets, and what the target is. One level lower when a connect from the source timed out or found "no route to host" instead of "network is unreachable", and, for a name, when some containers' metadata couldn't be read (one of them might answer to it)
- **Probe:** not needed (Probe? no). A connect from the source confirms it ("network is unreachable"); one that is refused or accepted means a route exists, and WR015 doesn't fire
- **Supersedes:** WR016
- **Since:** v0.2 (M6)

## The pitfall

A Compose network with `internal: true` (or `docker network create --internal`) cuts its containers off from everything outside it. Docker gives them no default route: they reach the other containers on the network, and nothing else. That is what people want for a database's network, until a service on it needs an outside API, a database on the LAN, or a service on the host:

```
connect: network is unreachable
getaddrinfo EAI_AGAIN api.example.com
Temporary failure in name resolution
```

The connect fails at once, without sending a packet, and names outside Docker don't resolve: Docker's embedded DNS doesn't forward lookups from internal networks, it answers SERVFAIL at once (both measured on Engine 29.9.3).

A container on an internal network and also on one without `internal: true` (or on Docker's default bridge) has a way out through that network: WR015 doesn't fire for it.

## The evidence

| Evidence | What it shows |
|---|---|
| `docker.container` of the source (for `network_mode: container:X`, of X) | every network it is on is `internal: true` (from Docker's network list), with each network's subnets |
| the target | it is outside them: the host (`host.docker.internal`, a name `extra_hosts` map to `host-gateway`, or one of the host's addresses), an address on none of the source's subnets, or a name with a dot that no container on any network answers to |
| `host.addrs` (for a host target) | which host address and interface the target stands for |
| `probe.tcp` from the source (optional) | the connect failed at once with `ENETUNREACH` ("network is unreachable") |
| `probe.dns` from the source (optional, for a name) | Docker's DNS answered SERVFAIL |

With probe containers off, metadata alone settles it. With them on, a connect to an address outside the probe allowlist (by default loopback, RFC 1918 and Docker's networks) is skipped, and metadata settles it the same way.

## The fix

Give the service a way out: attach it to a network without `internal: true` as well, and keep the internal network for the services that must stay cut off. In Compose:

```yaml
services:
  api:
    networks: [backend, default]   # backend stays internal; default is the way out

networks:
  backend:
    internal: true
```

When the project's `default` network is the internal one, declare another network without `internal: true` and add it instead. Without Compose: `docker network connect <network> <container>` (Docker's default `bridge` network works too). If the service must stay cut off and needs a service on the host, run that service as a container on the internal network instead.

## False positives and limits

- **The host through the network's own gateway address.** Docker still gives an internal network's bridge its gateway address on the host, and a container reaches the host there: a connect to it was refused with nothing listening and accepted with a listener (Engine 29.9.3). So a target on one of the source's subnets is never outside, and WR015 stays quiet; whatever is wrong there is a listener's problem (WR001, WR012).
- **A container on another network** is WR004's: the two share no network, whatever the networks' flags.
- **An address on the source's own subnet that no container holds** is a stale or hard-coded address (WR024, v0.2), not a missing way out.
- **A single-label name** that no container answers to is more likely mistyped (WR005). WR015 judges only names with a dot.
- **Routes added inside the container** (with `NET_ADMIN`) can give it a way out after all: a connect that is refused or accepted, or that times out, says so, and WR015 doesn't fire or drops a level.
- **When Docker's network list can't be read,** whyreach doesn't know which networks are internal, and WR015 doesn't fire.
- **Docker Desktop:** whyreach decides from Docker's metadata, which describes Docker Desktop's VM, so WR015 doesn't depend on the platform. Internal networks are expected to cut containers off there too; the WSL2 lab's run B (`docs/wsl2-lab.md`) checks it on Windows.

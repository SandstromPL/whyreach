# WR021: the host's firewall rejects container-to-host traffic

- **Layer:** 4, path
- **Confidence:** high when the host answers its own connect to the same address and port (accepted, or refused because nothing listens there) while the container's connect is rejected ("no route to host"), dropped (a timeout) or refused with a reset; high too when the host's own connect is rejected as well (a rule for the port, whoever connects). One level lower when the container runs in another container's network namespace, where a VPN client's kill switch would do the same, unless the host's own connect was rejected too. Without the host's own connect (it couldn't be made): medium for a reject, or for a drop in front of a listener that takes the address with an empty accept queue; low for a reject when the host's listening sockets couldn't be read either
- **Probe:** yes. Without the source's connect, WR021 isn't evaluated, and the probe's gap says how to allow it. The host's own connect needs no probe container
- **Supersedes:** WR016, for a timeout it explains
- **Since:** v0.2 (M6)
- **Frequency rank:** 9 (`docs/research/failure-signatures.md`, signature 9)

## The pitfall

A service on the host works from the host itself, and from a container it doesn't. A host firewall lets the host's own traffic through (it arrives on the loopback interface, which ufw, firewalld and hand-written rules accept) and filters what comes in on Docker's bridges, which its defaults don't let in:

```
$ nc -vz host.docker.internal 5432        # in the container
nc: connect to host.docker.internal (172.17.0.1) port 5432 (tcp) failed: No route to host
$ nc -vz 172.17.0.1 5432                  # on the host
Connection to 172.17.0.1 5432 port [tcp/postgresql] succeeded!
```

How the firewall turns the connect away decides what the container sees. Measured in M6 (ADR 0002's amendment), in a network namespace standing in for the host (a veth pair for a bridge and its container, a dummy interface for a LAN address, documentation addresses), with nftables rules inside it only:

| The host's firewall, for the port | The container's connect | The host's own connect to the same address |
|---|---|---|
| accepts loopback and established traffic, drops the rest (ufw's default "deny incoming") | times out | accepted |
| accepts loopback, rejects the rest with `icmp-host-prohibited`, `admin-prohibited` or `host-unreachable` (firewalld; RHEL's iptables rules) | "no route to host" (EHOSTUNREACH) at once | accepted |
| accepts loopback, rejects the rest with a TCP reset or `port-unreachable` (ufw's reject rules; nftables' plain `reject`) | "connection refused" at once | accepted |
| either of those, and the service listens on `127.0.0.1` only | times out, or EHOSTUNREACH | refused |
| drops or rejects the port for every source, loopback included | times out, or EHOSTUNREACH | the same |
| no rule on the host, but one in the container's own network namespace | times out, or EHOSTUNREACH | accepted |
| no rule, and the service has stopped accepting (a full accept queue) | times out | times out |

The comparison names the host's firewall without reading it: the host's own connect gets an answer, the container's doesn't, or gets a reject.

## Which rule takes which error

For a container's connect to one of the host's own addresses (`host.docker.internal` through `host-gateway`, a network's gateway, a LAN address):

| The container's connect | The host's own connect | Rule |
|---|---|---|
| "no route to host" (EHOSTUNREACH) | any, or none | WR021 |
| timed out | accepted or refused, or rejected too | WR021, superseding WR016 |
| timed out | none, and a host listener takes the address with an empty accept queue | WR021 (medium), superseding WR016 |
| timed out | timed out | WR016: the host doesn't answer itself either (a full accept queue, or a rule for every source) |
| refused | accepted | WR021: a reject that sends a reset |
| refused | refused, or none | WR001, WR012, or WR006 for a port published on the host's loopback |
| "network is unreachable" (ENETUNREACH) | none | WR015 (an internal network) |

EHOSTUNREACH that isn't the host's is WR024's (an address on the source's own network that no container holds) or WR013's (a Docker subnet took the range).

## The evidence

| Evidence | What it shows |
|---|---|
| `probe.tcp` from the source | its connect through the target's name or literal address: rejected (EHOSTUNREACH), timed out, or refused |
| `probe.tcp` from the host, via `control` | whyreach's own connect from its network namespace, the host's, to the same address and port, for comparison |
| `netns.listeners` of the host | a listener that takes that address, and its accept queue |
| `host.addrs` | that the address is the host's own, and on which interface |
| `docker.container` of the source | the `extra_hosts` mapping, the networks whose subnets the fix allows, and a `network_mode: container:` namespace |

The host's own connect is made only when it can change the answer: after the source's connect to one of the host's addresses was rejected, timed out, or was refused while a listener of the host's takes that address; never for a port a container publishes there, and only where Docker Engine runs on whyreach's machine. It goes through the policy like every probe: one connect, then close, to the address and port the source's own connect went to (the allowlist admitted it there); the host's own addresses need no approval through MCP (`INITIAL.md` §10 Q15); it takes a token of the rate limit and counts as a probe sent in the audit log. When it times out, the diagnosis takes up to 2 s longer.

whyreach reads no firewall rules: nftables and iptables need root, ufw's state is in files whyreach doesn't read (only `resolv.conf` and `hosts`), and parsing firewall rules is out of scope (`INITIAL.md` §2.2).

## The fix

- **Let the container's network in to the port.** With ufw: `sudo ufw allow from 172.22.0.0/16 to any port 5432 proto tcp`. With firewalld: `sudo firewall-cmd --permanent --zone=trusted --add-source=172.22.0.0/16`, then `sudo firewall-cmd --reload` (or put the bridge in a zone that accepts it). With iptables: an ACCEPT rule for that subnet before the rule that rejects or drops it. The subnet is the source's network's: whyreach names it.
- **When the host's own connect was refused too,** nothing listens on that address either: after the firewall, make the service listen there (WR012 says how for a loopback-only service).
- **When the source runs in a VPN container's namespace,** look at that container's firewall as well: a kill switch needs the host's address in its outbound allowlist.

## False positives and limits

- **Run against a real host firewall once, in the owner's WSL2 lab** (run A, Docker Engine in WSL2, 2026-11-21): with ufw's default deny incoming (a drop) and with a reject rule for Docker's bridges (`icmp-host-prohibited`, as firewalld answers), WR021 was primary at high both times, and the host's own connect was accepted. The dev box has no firewall rules, and the lab never changes the host's firewall, routes or interfaces, so elsewhere WR021 rests on the measurements in a network namespace, 33 fixtures and engine tests. The lab's `wr016-host-stalled` makes the host's own connect for real, against a host service that stopped accepting: both connects time out, and WR021 stays out. The lab's `wr021-host-firewall` is WR021's own scenario, skipped unless `WHYREACH_LAB_HOST_FIREWALL` says a host firewall was set up for it. Where to run it is `INITIAL.md` §10 Q9: the WSL2 lab's run A, whose distro is the lab's own, with ufw turned on and then a reject rule (`docs/wsl2-lab.md`, step 8).
- **A firewall in the container's own network namespace looks the same.** A reject or a drop there (a VPN client's kill switch, rules an app with `NET_ADMIN` set) also lets the host's own connect through. For a source in another container's namespace the finding is a level lower and says so; a container's own rules can't be seen without root.
- **Docker Desktop.** On `wsl2-desktop`, and Docker Desktop elsewhere, the host the containers reach is Windows or macOS, behind Docker Desktop's own network stack: a connect from the WSL2 distro says nothing about it. WR021 doesn't fire there and makes no connect; the host's listening sockets are a gap, as for WR012.
- **A port a container publishes** at that address goes through Docker's NAT and docker-proxy, where the host's INPUT rules may not apply: WR021 judges the host's own services, and a timeout there stays WR016's. A port published on the host's loopback only is WR006's.
- **A refusal without the comparison** stays out: a `[::]` listener that takes IPv6 only can't be told from a dual-stack one in `/proc`, so a listener alone doesn't prove the host would have accepted.
- **From the host,** or a host-network container, the connect is the host's own: WR019 and WR016.
- **The WSL2 VM** (`wsl2-engine`): the host is the WSL2 VM, and its firewall is the one inside the WSL2 VM, not Windows'.
- **Privacy:** the host's own connect is recorded like the source's (address, port, outcome); a redacted report redacts its address as it redacts the source's connect's.

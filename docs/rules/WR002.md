# WR002: the service listens only on loopback inside its container

- **Layer:** 5, listener
- **Confidence:** high from the destination's listeners alone; no probe container or root needed
- **Supersedes:** WR001
- **Since:** v0.1 (M1)

## The pitfall

A server inside a container binds to `127.0.0.1` (or `::1`). Inside a container, loopback belongs to that container's own network namespace, so the server only accepts connections from inside its own container. Every other container, and the host, gets `ECONNREFUSED`.

Many frameworks default to loopback in development mode: Flask's `app.run()`, `vite`, `next dev` in some versions, Rails' `bin/rails server`, Django's `runserver`, and many hand-written servers that call `listen("localhost:8080")`.

```yaml
services:
  api:
    command: ["flask", "run", "--port", "8080"]   # binds 127.0.0.1:8080
  worker:
    environment:
      API_URL: http://api:8080                    # refused
```

## The evidence

| Evidence | What it shows |
|---|---|
| `netns.listeners` of the destination | every listener for the port is on `127.0.0.0/8`, `::1` or `::ffff:127.x`. Docker's embedded-DNS listener on `127.0.0.11` is ignored |
| `docker.container` of the destination | the container whose listeners were read, and its addresses |
| `probe.tcp` from the source (optional) | a connect to the destination's address on the port is **refused**: confirms the cause |

The listeners are read from the host through `/proc/<pid>/net/tcp{,6}`, after `/proc/<pid>/cgroup` confirms the PID belongs to the container (ADR 0001). This needs no root and no Docker write, so WR002 reaches high confidence in the default configuration.

## The fix

Make the server listen on all interfaces inside the container, then restart it:

- `0.0.0.0:8080` (IPv4) or `[::]:8080` (IPv6, usually dual-stack)
- for example `flask run --host 0.0.0.0`, `vite --host`, `rails server -b 0.0.0.0`, or a `HOST=0.0.0.0` setting

Binding to all interfaces inside a container is safe: the container's network namespace is isolated, and only the ports you publish are reachable from outside the host.

## False positives and limits

- If a TCP connect from the source to the destination's address **succeeds**, the listener table is out of date (the server re-bound between the two reads) and WR002 does not fire.
- If nothing listens on the port at all, that is WR001, not WR002.
- The source can be the host or even the destination's own network namespace: a socket bound to 127.0.0.1 refuses connections to the container's network address from anywhere, itself included. Only a `localhost` target reaches it, and that is WR007's territory.
- A destination with `network_mode: host` listens in the host's namespace: that is WR012, not WR002.
- With replicas behind one name, a loopback-bound replica fails only the connections that reach it: when another replica serves, WR002 is one level less confident and says which ones serve.
- A timeout instead of a refusal points at the path, not at the listener: see WR004 and, from v0.2, WR016.

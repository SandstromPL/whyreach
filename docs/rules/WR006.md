# WR006: a host-published port is used between containers

- **Layer:** 2, addressing
- **Confidence:** between containers, high when the destination's listeners show a socket other containers can reach on the container port; medium when they can't be read, show nothing there (its server is down too: WR001 says so as "also found"), or show it on loopback only. Through the host's address, high from the port bindings alone
- **Supersedes:** WR003, WR012
- **Since:** v0.1 (M2)

## The pitfall

A port mapping such as `ports: ["18090:8080"]` applies only to connections arriving at the **host**. Another container on a shared network talks to the container directly, where the port is still 8080:

```yaml
services:
  weblo:
    ports: ["127.0.0.1:18090:8080"]
  client:
    environment:
      API_URL: http://weblo:18090   # refused: inside, weblo listens on 8080
```

The variant: reaching a published port **through the host's address** (`host.docker.internal:18090`), which fails when the port is published on `127.0.0.1` only.

## The evidence

| Evidence | What it shows |
|---|---|
| `docker.container` of the destination | its port bindings: the container port behind the host port the client uses |
| `netns.listeners` of the destination | it listens on the container port, not on the host port's number |
| `probe.tcp` from the source (optional) | refused |

## The fix

- Between containers on a shared network, use the container port: `weblo:8080`.
- Through the host: connect directly to the container over a shared network instead, or publish the port on every address.

## False positives and limits

- If the destination also listens on the host port's number inside, WR006 doesn't fire.
- If the port is published on every address, connecting through the host works: no WR006. Through the host's address the host's firewall can still be in the way (`docs/research/failure-signatures.md`, signatures 9 and 17): for the host's own services that is WR021, which compares the container's connect with the host's own to the same address and port. A port a container publishes goes through Docker's NAT, where whyreach doesn't judge the firewall (a timeout there stays WR016's), so the steadier fix is the direct one above: connect over a shared network.
- From the host itself, the published port is the right one.
- The through-the-host variant fires only on Linux Docker Engine: Docker Desktop forwards the host's loopback to containers, so a port published on `127.0.0.1` works there through `host.docker.internal`.

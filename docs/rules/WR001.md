# WR001: nothing listens on the port

- **Layer:** 5, listener
- **Confidence:** high, from the destination's listeners; a refused connect confirms it
- **Supersedes:** nothing; many rules supersede it
- **Since:** v0.1 (M2)

## The pitfall

Nothing in the destination's network namespace (a container's, or the host's when the target is the host) listens on the port. The server crashed inside a running container, never started, failed to bind, or serves UDP only.

"Connection refused" alone proves nothing: at least nine rules produce it (`docs/research/rule-experiments.md`). WR001 is what remains when the others don't explain it, and they supersede it when they do:

| Better explanation | Rule |
|---|---|
| the destination is down or restarting | WR008 |
| the destination is still starting | WR010 |
| `localhost` used inside a container | WR007 |
| the host's port isn't published | WR019 |
| it listens on loopback only | WR002, WR012 |
| it listens on another port | WR003 |

## The evidence

| Evidence | What it shows |
|---|---|
| `netns.listeners` of the destination | nothing on the port, and nothing reachable from outside on any other port |
| `docker.container` of the destination | the container, and the published port the connection came through, if any |
| `probe.tcp` from the source (optional) | refused, or accepted and closed at once by docker-proxy |

## The fix

Check that the server started and listens on the port: `docker logs <container>`, its port setting, and whether it serves TCP at all. On the host, start the service or check its port.

## False positives and limits

- Missing listener evidence is never a negative result: if the listeners can't be read, WR001 doesn't fire.
- If a connect got through, the listener table is out of date: no finding.
- whyreach reads TCP listeners only; a UDP-only service looks like nothing listening.
- When the target port is a host port the destination publishes for another container port (WR006), WR001 checks the container port, the one WR006's fix points to.
- With replicas behind one name, a replica that listens on nothing fails only the connections that reach it: when another replica serves, WR001 is one level less confident, names the replica by its container name and says which ones serve.
- A connect from the source that **timed out** or found no route, instead of being refused, contradicts a listener finding: something on the path (a host firewall, say) stops the connection too, and fixing the listener may not be enough. The finding is one level less confident and cites the connect as contradicting evidence.

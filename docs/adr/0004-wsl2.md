# ADR 0004: Windows through WSL2

- **Status:** accepted (M6, 2026-11-14). Built; the owner's manual lab runs on Windows passed on 2026-11-21 (`docs/wsl2-lab.md`, the amendments below), and WSL2 is claimed for v0.2.
- **Answers:** `INITIAL.md` §3.7 items 4 and 6, and how §6.3's lab runs inside WSL2
- **Builds on:** ADR 0001 (probe containers, listeners from the host, the netns executor and its M3 amendment), ADR 0003 (consent for probe containers)

## Context

v0.2 reaches Windows by running the Linux build inside a WSL2 distro (§3.7). Two setups matter, and they differ where it hurts:

| | `wsl2-engine` | `wsl2-desktop` |
|---|---|---|
| Docker | Docker Engine installed in the distro | Docker Desktop's WSL integration: the distro gets a socket to Docker Desktop's engine |
| Where the containers run | in the distro | in Docker Desktop's VM |
| Docker's PIDs | processes in the distro: `/proc/<pid>` and `setns` work | processes in another PID namespace: a `/proc/<pid>` read or a `setns` would reach an **unrelated local process** |
| whyreach's "host" | the WSL2 VM, not Windows | the WSL2 VM, not Windows |
| The host containers reach (`host.docker.internal`) | the WSL2 VM, through a `host-gateway` mapping | Windows (Docker Desktop provides the name) |

The dev box has Docker Engine only, and the owner declined Docker Desktop for Linux there; the owner has a Windows PC with WSL2. So the detection and the gating are built and tested on fixtures here, rehearsed against a Docker that claims to be Docker Desktop, and validated by hand on Windows.

## Decision 1: classify the platform, record it as evidence

`platform.Classify` names the setup from where whyreach runs (`platform.Detect`) and what the daemon says about itself (`GET /version`): `linux-engine`, `wsl2-engine`, `wsl2-desktop`, and, for v0.3, `linux-desktop`, `macos-desktop` and `windows-desktop`; `other` covers no Docker API, Windows containers, and whyreach inside a container on Docker Desktop (M7).

- **WSL2** needs three things: the kernel's name says `microsoft` (only a hint), WSL's interop entry is registered (`/proc/sys/fs/binfmt_misc/WSLInterop`, or `WSLInterop-late`, the name WSL uses when systemd is on), and whyreach isn't in a container, whose kernel name is the same. A container runtime in PID 1's cgroup means a container. WSL's init registers the interop entry and containers don't see it (binfmt_misc isn't mounted in them), so with the entry present, `/.dockerenv` and `/run/.containerenv` don't count: a distro imported with `wsl --import` from a `docker export` keeps the export's `/.dockerenv` (found by the review). A distro with interop turned off is classified as plain Linux: the host's side is then labelled "the host", and nothing unsafe follows, since the PID decision below doesn't depend on WSL.
- **Docker Desktop** is the daemon whose platform name says so (`Docker Desktop 4.x.y`), as `docker version` prints it.
- **Inside a container**, whyreach can't see WSL's marker; on Docker Engine whose kernel is WSL2's it classifies `wsl2-engine` (Docker Desktop's daemon says its own name), and its view of the host still comes from Docker's answer about its own container (§3.5).
- The engine records the result as a `platform` evidence record in every diagnosis (numbered after `docker.version`), and rules read it from the view. Rules that predate it fall back to `docker.version`'s identity for evidence made without it.

## Decision 2: Docker's PIDs are whyreach's only where Docker Engine runs here

`platform.EngineHere` is true for `linux-engine` and `wsl2-engine` only. Everywhere else:

- **No `/proc/<pid>` read, no `setns`.** The engine never asks the listener reader about a container, and never picks the netns executor, even as root (the CLI still builds it; the engine doesn't use it, and `doctor` says why). The cgroup check (`/proc/<pid>/cgroup` must name the container) stays as a second line of defence, but the decision doesn't lean on it.
- **Listeners come from probe containers.** A container's listening sockets are read by a probe container joined to its network namespace, the path ADR 0001 verified for Docker Desktop. Each read is a container run and a probe token, so a diagnosis makes at most 6 of them: the source's (for a loopback target) and the destinations' first, then the peers'. The rest become skipped records and one gap. On Docker Desktop the default 30 probes a minute therefore allows about three diagnoses a minute in an MCP session; `rate_per_minute` is the knob. The bound picks the same containers every time; the rate limit, which the parallel reads draw on, can refuse some of them, and close to it which ones depends on timing.
- **Without probe containers** the record is `unsupported`, with `executor.PIDsElsewhere` as its reason, and the gap says how to allow them. The policy treats that record like a probe that needed one, so an MCP client's user is asked for probe containers when they'd change the answer (ADR 0003, Decision 1).
- This reuses how whyreach's image handles PIDs that aren't its own (`--pid host`, M4): a record that says why, never another process's sockets passed off as the container's.
- **Known edge:** Docker Engine run in one distro and shared with another through its socket (a setup some use instead of Docker Desktop) looks like `wsl2-engine` from the second distro, but Docker's PIDs are the first distro's. The cgroup check refuses them, so the listener records fail with that reason instead of describing a local process, and as root the netns executor can't enter and hands the batch to a probe container when they are allowed (ADR 0001's M3 amendment). Safe, but less useful than reading them in probe containers; not built until someone asks.

## Decision 3: under WSL2, the host's side is the WSL2 VM

- Host-side records (`host.addrs`, the host's listeners, probes from the host, the platform record itself) carry a context named `WSL2 VM`, and facts, gaps and rule prose say "the WSL2 VM" where they said "the host". When a diagnosis involves the host's side, one fact says that whyreach runs in WSL2 and the host's side is the WSL2 VM, not Windows.
- **On `wsl2-desktop`, the host a container reaches is Windows** (through `host.docker.internal` or `host-gateway`), or Docker Desktop's VM for `network_mode: host`. whyreach can read neither from WSL. So for a container source, the host's listeners are an `unsupported` record (`executor.HostNotHere`), not the VM's sockets, unless the container aims at one of the VM's own addresses; the gap says how to check on Windows by hand. WR012 never concludes from the VM's state there, and WR013 (v0.2, Phase 2) records a gap in the same way. No Windows collector is built (§3.7: only on demand).
- **WR011 fires only on Docker Engine** (`linux-engine`, `wsl2-engine`), read from the platform record; Docker Desktop provides `host.docker.internal` on every platform. **WR006**'s variant through the host's loopback stays off on Docker Desktop. **WR019**'s hint that the host can reach a container's own address appears only where Docker Engine runs here: Docker Desktop's container addresses live in its VM.

## Decision 4: launching from Windows MCP clients

- The command is `wsl.exe -d <distro> --exec /abs/path/whyreach mcp serve`. `--exec` runs the binary without a shell, so profile files don't matter; the server runs as the distro's default user.
- Settings go in as flags: a Windows client's environment doesn't cross into WSL unless `WSLENV` lists it. `--log-level` joins `WHYREACH_LOG` for that reason; permissions live in the config file in the distro, which needs no variable. `DOCKER_HOST` isn't needed: both setups provide `/var/run/docker.sock`.
- The server exits as soon as its input ends: when a client goes away, that is all the server sees. `TestMCPServeExitsOnStdinEOF` runs the real binary, closes its input before any request and after `initialize`, and requires exit status 0 within 3 s (it takes milliseconds).
- **The launch check** (`test/wsl2/mcp-launch.ps1`, step 5 of the manual runs) does from Windows what a client does: it starts whyreach through `wsl.exe` with pipes and requires answers to `initialize` and `tools/list`, a WSL2 platform from `inspect_environment`, and an exit within 5 s of its input closing with no server left behind. While Docker doesn't answer yet, it asks again for up to 20 s: whyreach asks Docker afresh on every call, so a Docker that starts after it shows up on the next one. With `-Cold` it first shuts WSL down (`wsl --shutdown`), so `wsl.exe` boots the WSL2 VM and the distro, as a client meets them after WSL stopped the idle distro and then the idle VM; on `wsl2-engine`, `dockerd` then starts with the distro. It does that only where `docker version` in the distro names Docker Engine (found 2026-11-15): Docker Desktop keeps a `wsl.exe` session open in each distro it integrates with (its proxy), so the distro doesn't go idle while Docker Desktop runs, and shutting WSL down would stop Docker Desktop's engine too. Like the GUI clients (Node's `windowsHide`), it starts `wsl.exe` without a console window. The script was exercised with PowerShell 7 on Linux against a stand-in `wsl.exe` and the real binary (warm and cold starts, a Docker socket that appears late, no Docker, a platform that isn't WSL2's, Docker Desktop's skip, a `docker version` that names no Docker Engine, no `pgrep`, a stray line on standard output); Windows PowerShell 5.1's console encoding is first tested in the owner's runs.
- `doctor`, in WSL2, prints the `wsl.exe` command with the distro's name (`WSL_DISTRO_NAME`).
- The README said nothing about WSL2 until the manual runs passed (the amendments below); `docs/wsl2.md` holds the setup. The help text names no platform.

## Decision 5: `doctor`

- A `platform` line names the setup and what it means for whyreach's checks.
- On `wsl2-engine` a warning: WSL stops a distro about 15 seconds after its last terminal or `wsl.exe` command closes (`instanceIdleTimeout` under `[general]` in `.wslconfig`), and the VM once all distros have stopped (`vmIdleTimeout`); services such as `dockerd` don't keep it running (microsoft/WSL issue 8854), so `dockerd` and every container stop with it; the fix names `instanceIdleTimeout=-1` in `%UserProfile%\.wslconfig` and says Docker recommends Docker Desktop over Docker Engine in WSL2 (§3.7).
- The container-listeners line says that on Docker Desktop listeners are read in probe containers, never through `/proc/<pid>`.

## Decision 6: the lab inside WSL2

The lab (`make lab`) must pass inside WSL2 under both setups, run by hand on the owner's Windows PC (`docs/wsl2-lab.md`, `test/wsl2/run-lab.sh`). GitHub-hosted runners can't be that gate (§3.7, item 5).

- **The harness classifies its platform** as whyreach does and prints it first.
- **With probe containers on**, every scenario's `expect` must hold exactly, on both setups: on `wsl2-desktop` the listeners come from probe containers. There, in every run, the harness checks that every listener read that worked came from one, and that none went through `/proc/<pid>`, whether it worked or not (records of such a read carry `engine.ProcListenerSource`). It also checks that whyreach recorded the platform the lab found, since the expectations depend on it.
- **With the default config on `wsl2-desktop`** (no probe containers), containers' listeners can't be read at all, so `expect_without_probe` can't hold. Instead the diagnosis must degrade honestly: the expected verdict or a weaker one (no problem reproduced may only become inconclusive), the primary finding, if any, the expected rule at no higher confidence, nothing in `must_not_fire`, and, when weaker, a gap that says how to allow probe containers. A scenario whose honest answer there is another rule says so in `expect_desktop_without_probe`: only `wr019-not-published`, where whyreach can't see that the container serves the port, so "nothing on the host listens" (WR001) is likely, not settled, and its fix still says to publish the port.
- **Where a scenario's premise doesn't hold**, `expect_on: {<platform>: {verdict_in, must_not_fire}}` replaces both expectations: WR011's and WR012's scenarios on `wsl2-desktop`, where Docker Desktop provides `host.docker.internal` and the host it reaches is Windows. They must not fire, and the verdict may be either no problem reproduced or inconclusive, depending on whether Windows forwards the port into WSL. `skip_on` exists for a scenario that can't run on a platform; none uses it.
- **`host_listen: docker0`** listens on loopback where Docker's bridges aren't this machine's (Docker Desktop).
- **`make lab-root`** runs on `wsl2-engine` only (an optional step): on `wsl2-desktop` the netns executor doesn't run, by Decision 2.
- **A rehearsal on the dev box:** `make lab-desktop` runs the lab with whyreach behind a Docker API proxy whose `GET /version` says Docker Desktop, so the Docker Desktop path runs against real containers: listeners from real probe containers, no `/proc/<pid>` read, the degraded checks, and `wsl2-desktop`'s expectations. The dev box isn't WSL2, so whyreach classifies it `linux-desktop`: `wsl2-desktop`'s `expect_on` entries pass there because WR011 and WR012 stay off on any Docker Desktop, while the Windows host's unsupported record (`executor.HostNotHere`), the WSL2 VM's labels and the WSL2 fact run only in unit tests until the owner's run B, their first run against real containers (found by the review). Nor can it show the rest of Windows' side (`host.docker.internal` reaching Windows, published ports forwarded into WSL). Its first run found a real bug: the host's search for a container that serves a port unpublished (WR019) dropped containers whose sockets it couldn't read, so WR001 claimed "nothing listens" at high confidence. Unread sockets are now one record and a gap, and WR001 drops to medium from the host when any went unread (whyreach's image without `--pid host` had the same hole).

## Amendment (2026-11-21): the first manual runs

The owner ran both setups on Windows (WSL 3.0.5, NAT networking) with the bundle of `6e205ce`:

- **Run A** (Ubuntu 24.04, Docker Engine 29.10.0): the unit tests, `doctor` (`wsl2-engine`), `make lab` and `make lab-root` passed. `demo-localhost` was skipped in every run, as the lab pulls no image and `python:3.13-slim` wasn't there.
- **Run B** (Debian, Docker Desktop 4.99.0 with Engine 29.9.3): the unit tests and `doctor` (`wsl2-desktop`) passed; `make lab` passed 19 of 20 scenarios. `wr005-unknown-name` failed with probe containers: Docker Desktop's DNS, Docker's embedded DNS's upstream there, didn't answer the single-label name `apii` within the probe's 2 s, twice, so WR020 fired high ahead of WR005. The lookups of single-label names in `wr004` and `wr009` took as long. Fixed: WR020 judges only names with a dot (for a single-label name, the search-domain names the resolver tried), since no upstream resolves a single-label name; and WR005 is high when a single-label name asked as it is times out at Docker's embedded DNS while the source's own name resolves there, since Docker's DNS passes on only the names Docker doesn't know.
- **The launch check** failed in both runs before whyreach started. It quoted the distro's name (`-d "Debian"`), and `wsl.exe` reads `-d`'s value up to the next space, quotes included, so it found no such distribution. Clients pass the name as it is, and the script does too now.
- Still to run, with a new bundle: the launch check in both setups, and run B's lab. Until they pass, WSL2 stays unclaimed.

## Amendment (2026-11-21): the second runs pass

The same day, with the bundle of `ef5134c` (both fixes above):

- **Run A** (Ubuntu 24.04, Docker Engine): `make lab` and `make lab-root` passed all 20 scenarios. The launch check passed from a running distro (`initialize` answered 157 ms after the start) and after `wsl --shutdown` (3.9 s, booting the WSL2 VM and the distro; Docker answered on the first call).
- **Run B** (Debian, Docker Desktop): `make lab` passed all 20 scenarios, `wr005-unknown-name` with WR005. The launch check passed from a running distro (116 ms); its cold start is skipped by design.
- In each launch, whyreach listed its four tools, reported the setup's platform, exited within 10 ms of its input closing, and left nothing running. No probe container was left behind.
- The optional step with a real client (Claude Desktop or VS Code on Windows) brought back no result: the clients' configurations in `docs/wsl2.md` follow their documented formats and haven't each been tried.

So WSL2 is claimed for v0.2: the README and `docs/wsl2.md` say so, and that the v0.1.0 release doesn't have it. Before v0.2 is tagged, the lab runs again in both setups with the six new rules' scenarios.

## Consequences

- Rules that depend on the platform read the `platform` record; `docker.version`'s `linux_engine` stays in the JSON, meaning Docker Engine on whyreach's own machine.
- `inspect_environment` (host) reports the platform, and under WSL2 its summary says the host's side is the WSL2 VM.
- Docker Desktop costs more probe containers per diagnosis than Docker Engine did, within the bound above.
- Still open: `INITIAL.md` §10 Q7 (probe containers under Enhanced Container Isolation) needs a Docker Desktop business setup to test; the owner's PC has none, so it stays open for M7. Host-network containers on Docker Desktop (WR023) stay in v0.3.
